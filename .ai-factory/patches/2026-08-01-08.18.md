# Partner payment idempotency leaked replay across orders

**Date:** 2026-08-01 08:18
**Files:** app/Services/Partner/PartnerPaymentService.php, tests/Feature/PartnerApi/PartnerOrderHttpTest.php, tests/Feature/PartnerApi/PartnerDocumentationTest.php, resources/openapi/partner-v1.json, docs/PARTNER_API.md
**Severity:** critical

## Problem

One partner could reuse the same payment Idempotency-Key and payment method for two different PartnerOrder records. The second request returned the first order's payment as a successful replay.

## Root Cause

The canonical payment request hash contained only payment_method_id, while the idempotency ledger lookup was intentionally scoped by partner and key. The replay path assumed that a matching hash also implied a matching order, but no order identity was included or checked.

## Solution

Included partner_order_id in the canonical request hash and explicitly compared the existing ledger's partner_order_id with the locked requested order. The same guard is applied after a unique-index race. Added an HTTP regression test proving that reuse across two orders returns 409 and does not call the gateway or create another transaction. OpenAPI and Partner API documentation now describe the key constraints and order binding.

## Prevention

- Include every operation identity boundary in an idempotency request hash.
- Validate stored ownership and target identifiers independently of a payload hash.
- Cover cross-resource key reuse in HTTP tests, not only changed payloads on one resource.
- Keep the database unique constraint as the final concurrent-insert guard.
